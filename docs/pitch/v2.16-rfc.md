# RFC: `grok-agent.yaml` v2.16 — Federated Trust, Inter-Agent Capability, and xAI Co-Governance

Built for xAI, X, Grok and the ecosystem community. ❤️

## Abstract

This memo proposes seven additive changes to the `grok-agent.yaml` manifest
standard, advancing it from v2.15 to v2.16. The changes target three problem
areas the ecosystem has surfaced in the first six months of v2.15 deployment:
(1) agents that need to discover and call other agents safely, (2) end users
who need a portable trust signal before installing an agent on a Windows
machine they own, and (3) the absence of a formal channel for xAI engineering
to bless, sign, or veto entries in the public marketplace. The proposal is
strictly additive — every v2.15 manifest validates as v2.16 unchanged — and
every field below is offered as a starting point for xAI input, not a
finished design.

## 1. Introduction

The v2.15 spec, released 2026-05-04, established a single source-of-truth
manifest covering agent identity, tool surfaces, safety gates, real-time X
hooks, and Windows-native install paths. Six months in, three patterns have
emerged that v2.15 cannot cleanly express:

1. **Inter-agent calls.** Super Agents increasingly want to invoke each
   other's tool surfaces (e.g. the Living Narrative Fabric pulling a payout
   forecast from the Creator Payout Optimizer). v2.15 has no field for an
   agent to advertise its callable surface to *other agents*.
2. **Portable trust.** The marketplace shows install counts, but a user
   inspecting a manifest before install has no machine-readable trust signal
   — only a free-text description.
3. **xAI governance gap.** There is no slot in the manifest reserved for an
   xAI-controlled signature, which means there is no on-ramp for xAI to
   formally bless, certify, or revoke an agent.

v2.16 addresses each of these with a small, additive field. None of the
fields are required. Each is opt-in, each defaults to a safe value, and each
is parseable by the existing scanner with a one-line schema extension.

This memo's relationship to v2.15 is the same as v2.15's relationship to
v2.14: a layer on top, never a rewrite underneath.

## 2. Terminology

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **MAY**,
**REQUIRED**, and **OPTIONAL** in this document are to be interpreted as
described in BCP 14 (RFC 2119 + RFC 8174) when, and only when, they appear
in all capitals.

For convenience:
- **Manifest** — a single `grok-agent.yaml` file declaring one agent.
- **Surface** — any tool, prompt template, or callable function an agent
  exposes to a runner or to other agents.
- **Bless** — an xAI-signed attestation that an agent has passed an xAI
  internal review. Distinct from "validates against the schema".
- **Consent broker** — a separate process or service that mediates user
  consent across multiple agents.

## 3. Proposed Changes

Each subsection presents one proposed field, the rationale for adding it
now, and an illustrative YAML snippet. Every field is **OPTIONAL**.

### 3.a `exposes:` — Agent-to-Agent Capability Advertisement

**Rationale.** v2.15 has a `tools:` block describing what an agent calls,
but no symmetric block describing what an agent *offers*. As Super Agents
mature, the natural pattern is for one agent to call another agent's tool
surface over MCP rather than re-implement the same connector. Without a
formal advertisement field, callers must read the entire downstream agent's
source to discover its callable surface, which defeats the manifest's
purpose. We propose `exposes:` as a sibling of `tools:`, listing each
surface this agent makes available to *other* agents via MCP, including the
input schema, output schema, and an explicit `consent_required` flag.

The field is opt-in: an agent that does not want to be callable simply
omits `exposes:` and remains invisible to peer-discovery. We expect the
field to be empty for the majority of v2.16 agents and only meaningful for
Super Agents and shared utilities. xAI input is invited on whether the
schema language should be JSONSchema, OpenAPI fragments, or a Grok-specific
shorthand.

```yaml
exposes:
  - surface: "forecast_payout"
    description: "Returns a 30-day USD payout forecast for an X handle."
    input_schema:
      handle: { type: "string", pattern: "^@[A-Za-z0-9_]+$" }
      horizon_days: { type: "integer", default: 30 }
    output_schema:
      forecast_usd: { type: "number" }
      confidence: { type: "number", minimum: 0, maximum: 1 }
    consent_required: true
    rate_limit_per_minute: 10
```

### 3.b `trust:` — Federated Trust Score Declaration

**Rationale.** The marketplace will eventually need a sortable trust column.
Today, there is no standard place for an agent to publish its self-reported
trust score, the date of the most recent third-party evaluation, or a
pointer to a signed attestation. We propose a `trust:` block holding three
fields: `self_score` (0.0–1.0, the agent author's own claim), `last_eval`
(an ISO-8601 timestamp from the most recent Promptfoo/DeepEval run), and
`attestation_url` (a pointer to an Ed25519-signed JSON document hosted by
either the author or an accredited third party).

The block is advisory, not authoritative. The runner displays the score but
does not gate execution on it. xAI input is invited on whether the
attestation format should reuse the Sigstore bundle format, an SPDX-style
attestation, or a fresh Grok-native format.

```yaml
trust:
  self_score: 0.78
  last_eval: "2026-04-22T14:03:11Z"
  attestation_url: "https://attestations.agentmindcloud.dev/forecast-payout-v3.sig"
  attestation_format: "sigstore-bundle-0.3"
```

### 3.c `real_time_x.subscriptions:` — Inter-Agent Real-Time Triggers

**Rationale.** v2.15's `real_time_x:` block lets an agent subscribe to
public X events (mentions, cashtags, keywords). It does not let an agent
subscribe to *another agent's* events — for example, "fire whenever the
Cashtag Alpha Engine flags a regime change". We propose extending the
existing block with a `subscriptions:` array whose items reference an
upstream agent's `exposes:` surface plus an event name. The runtime
delivers the event payload as the trigger context for this agent's loop.

This unlocks pub/sub composition without requiring agents to share a
database or scrape each other's output. xAI input is invited on the wire
protocol — gRPC, MCP, or a Grok-specific event stream — and on the back-
pressure model when one agent emits faster than its subscribers can
consume.

```yaml
real_time_x:
  enabled: true
  subscriptions:
    - upstream_agent: "x-smart-cashtag-alpha-engine"
      surface: "regime_change_event"
      delivery: "mcp.event-stream.v1"
      max_lag_seconds: 5
```

### 3.d `grok.prompt_fingerprint:` — Versioned Prompt Provenance

**Rationale.** Today an agent's system prompt can drift between releases
without any record on the manifest itself. The Living Narrative Fabric
already hashes its own prompts internally; we propose lifting that pattern
to the manifest layer so any tool — the marketplace, the validator, a
trust attestor — can detect drift. The fingerprint is the SHA-256 of the
canonicalized system + user prompt templates, plus the model identifier and
a human-readable revision label.

This field is the cheapest possible win for provenance: a single string
that lets the validator say "the prompt that produced trust score 0.78 on
April 22 is the same one shipping today, or it is not". xAI input is
invited on canonicalization rules (whitespace, ordering, included files)
and on whether xAI would prefer to host a public ledger of fingerprints.

```yaml
grok:
  model: "grok-4.3-latest"
  prompt_fingerprint:
    sha256: "8e2c1f...a91"
    revision: "2026.05.09-r1"
    canonicalized_files:
      - "prompts/system.md"
      - "prompts/user_templates.md"
```

### 3.e `safety.cost_attribution:` — Downstream Billing Party

**Rationale.** When agent A invokes agent B which invokes the xAI API, who
pays? Today the answer is "whoever's API key is in the environment", which
is fine for solo developers and broken for orgs running shared agent fleets.
We propose a `cost_attribution:` block under `safety:` declaring the party
responsible for downstream costs incurred by this agent. Values are
deliberately abstract (`caller`, `author`, `installer`, or a literal
billing-account identifier) so that orgs and the eventual xAI billing system
can resolve them however they choose.

This field is the precondition for any future paid-tier marketplace and for
any xAI rev-share program. xAI input is invited on whether the field should
also carry a per-call ceiling, a monthly cap, or a hint to the runtime
about which API key to load. Misconfiguration MUST result in a refusal to
run, never a silent fallback.

```yaml
safety:
  cost_attribution:
    party: "installer"
    billing_account_hint: null
    max_usd_per_call: 0.50
    fail_closed: true
```

### 3.f `xai_blessed:` — xAI-Signed Status Indicator

**Rationale.** The marketplace needs a way to surface "xAI has reviewed this
agent". We propose a top-level boolean `xai_blessed:` whose only valid
writer is an xAI-controlled Ed25519 signing key. The validator MUST refuse
to set the field to `true` unless the manifest is accompanied by a
detached signature from a key on a published xAI key-list. The field is the
*minimum viable governance hook* — it does not gate install, it does not
gate execution, it only paints a visible badge in the marketplace.

This field is the door for xAI to walk through whenever they are ready,
and the absence of the door has been raised by every reviewer of v2.15.
xAI input is invited on the key-rotation policy, on whether the field
should carry a tier (e.g. `bronze`, `silver`, `gold`) instead of a boolean,
and on the legal language that accompanies a blessing.

```yaml
xai_blessed: false
xai_blessing:
  signature_url: null
  signed_by_keyid: null
  blessed_at: null
  tier: null   # one of: null, "bronze", "silver", "gold"
```

### 3.g `consent_broker:` — Inter-Agent Consent Contract

**Rationale.** When agent A calls agent B and B wants to take a real-world
action, whose consent gate fires? v2.15 says "the user always consents
explicitly", but it does not specify which agent owns the prompt when a
chain of three agents is involved. We propose a `consent_broker:` block
declaring which broker an agent will defer to for shared consent decisions,
plus the contract version. The broker is a separate process — it MAY be a
Grok-hosted service, a self-hosted Mastra workflow, or a stub that always
re-prompts the user.

This field is the missing piece for safe agent swarms. xAI input is
invited on whether xAI wants to host a reference broker, on the wire format
for consent requests, and on how to express revocation.

```yaml
consent_broker:
  broker_uri: "mcp://localhost:7421/consent-broker"
  contract_version: "1.0"
  defer_actions:
    - "post_to_x"
    - "send_dm"
    - "schedule_calendar_event"
  fallback: "refuse"   # if broker unreachable: refuse | local-prompt
```

## 4. Backwards Compatibility

v2.16 is strictly additive. Every field introduced above is **OPTIONAL**
and defaults to a safe value (`null`, `false`, or omission). A v2.15
manifest dropped into a v2.16 validator MUST validate without modification.
A v2.14 manifest dropped into a v2.16 validator MUST validate without
modification (transitively, via the v2.15 backwards-compat clause).

The validator (`safety/scanner.py`, `cli/grok-agent.py`) gains:
- One Pydantic model per new block.
- One Constitution article per field describing the safe default.
- Zero changes to existing models.

The Windows install path remains `$env:LOCALAPPDATA\grok-agent\` for all
v2.16 agents. The marketplace API gains optional response fields for the
new blocks; clients that ignore them MUST continue to function.

## 5. Migration Strategy

`grok-agent validate` auto-upgrades any v2.14 or v2.15 manifest to v2.16 in
memory before validation. Auto-upgrade is non-destructive — the on-disk
file is not modified unless the user passes `--write-upgrade`. The upgrade
path:

1. Read the manifest.
2. If `version:` is `2.14` or `2.15`, inject default v2.16 blocks (all
   defaulting to omission or `false`).
3. Validate against the v2.16 Pydantic model.
4. Report any failures with the original line numbers preserved.

Authors who want to opt into v2.16 features explicitly bump their
`version:` string to `"2.16"` and add the relevant blocks. There is never a
forced migration. The v2.15 spec remains the supported floor through 2027.

## 6. Security Considerations

The new fields introduce four security surfaces worth naming explicitly:

1. **`exposes:` enables remote callers.** An agent that advertises a
   surface MUST gate it with the same `consent_gates` and
   `forbidden_actions` lists that govern direct user invocation. The
   validator MUST refuse a manifest whose `exposes:` surface bypasses a
   gate that the local UI enforces.
2. **`trust.attestation_url` is an external dependency.** The runtime MUST
   treat the URL as untrusted input and verify the signature against a
   pinned key list before displaying the score.
3. **`xai_blessed:` is forgeable if the validator does not check the
   signature.** The validator MUST refuse the field as `true` whenever
   the accompanying signature is missing, expired, or from a key not on
   the published xAI key-list.
4. **`consent_broker:` introduces a network hop for consent.** The
   `fallback:` field MUST default to `refuse` so that a broker outage
   never silently approves an action.

The Constitution scanner gains one article per surface above.

## 7. Privacy Considerations

The new fields do not introduce any new user-data collection. Specifically:

- `exposes:` advertises only the agent's own callable surface — no user
  data leaves the local machine as a side effect of declaring it.
- `trust:` carries only the agent's own self-claimed score — no user
  identifier is required.
- `real_time_x.subscriptions:` reuses v2.15's existing privacy posture:
  events are delivered to the local runtime, never to a third party.
- `grok.prompt_fingerprint:` is a hash of the agent's own prompts — no
  user data.
- `safety.cost_attribution:` carries an opaque billing hint, never a
  user identifier without explicit consent.
- `xai_blessed:` carries no user data.
- `consent_broker:` carries the broker URI only; the broker itself is
  governed by its own privacy policy, which the validator MUST surface to
  the user at install time.

The local-first default of v2.15 carries forward unchanged: user data
lives at `$env:LOCALAPPDATA\grok-agent\` on the user's Windows machine
unless the user explicitly opts into cloud sync.

## 8. Open Questions

These are genuine open questions. The authors do not have a preferred
answer for any of them and are explicitly inviting xAI input.

1. **`exposes:` schema language.** JSONSchema, OpenAPI fragment, or a
   Grok-native shorthand? Each has a tradeoff between expressiveness and
   manifest readability. xAI's preference will likely decide this.
2. **`trust.attestation_format`.** Sigstore bundle, SPDX attestation, or a
   fresh Grok-native envelope? We lean Sigstore for ecosystem reuse, but
   xAI may prefer a format that matches its own signing infrastructure.
3. **`xai_blessed:` tiering.** A boolean is the simplest schema; a
   bronze/silver/gold tier is the most expressive. xAI may also prefer no
   such field at all and a separate registry — a counter-proposal we
   would welcome.
4. **`consent_broker:` reference implementation.** Should xAI host a
   reference broker, or should the ecosystem own it? A Grok-hosted broker
   gives stronger guarantees; an ecosystem broker gives stronger
   neutrality.
5. **`real_time_x.subscriptions:` wire protocol.** MCP event-stream is the
   default proposal, but a Grok-hosted pub/sub bus would be materially
   easier to operate at scale. xAI's input on whether such a bus is on
   their roadmap will shape this field.
6. **Versioning cadence.** v2.15 shipped six months ago; v2.16 is a small
   layer on top. Should the cadence be quarterly, semi-annual, or
   driven by demand? The authors lean semi-annual, but defer.
7. **Spec governance.** Should v2.17 onward be co-owned by an xAI engineer
   listed in the Authors' Addresses section, or remain author-owned with
   xAI as a reviewer? The authors prefer co-ownership and have left a
   placeholder in the Authors' Addresses section accordingly.
